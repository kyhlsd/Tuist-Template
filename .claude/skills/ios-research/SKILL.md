입력: $ARGUMENTS

두 조사를 **동시에** 띄웁니다. 당신은 조사하지 않고, 띄우고 전달만 합니다.

## 절차

1. **주제를 나눕니다.** 입력에 `|`가 있으면 앞은 플랫폼 조사 주제, 뒤는 저장소 조사 주제입니다.
   없으면 두 조사에 같은 입력을 씁니다.
2. **한 응답 안에서 Agent 툴을 두 번 호출합니다.** 응답을 나눠 호출하면 동시에 돌지 않습니다.
   프롬프트는 아래 두 섹션을 그대로 쓰고, `<주제>`만 1에서 정한 주제로 바꿉니다.
   - `subagent_type: ios-platform-researcher`, `run_in_background: true`.
     웹 검색만 쓰므로 백그라운드로 보냅니다.
   - `subagent_type: ios-researcher`, `run_in_background: false`.
     LSP가 필요하므로 반드시 포그라운드로 띄웁니다. 백그라운드 서브에이전트에서는 LSP가 빠집니다.
3. **도착하는 대로 전달합니다.** 저장소 조사가 먼저 끝나면 그 결과부터 전달하고,
   플랫폼 조사는 아직 돌고 있다고 알립니다. 완료 알림이 오기 전에 결과를 추측하거나 지어내지 않습니다.
   각 보고는 핵심 발견과 열린 질문 위주로 짧게 요약합니다. 원문은 대화에 남아 있어
   `/ios-plan`이 그대로 읽습니다. 두 조사를 대조하거나 결론 내지 않습니다. 대조는 `/ios-plan`이 합니다.
4. 두 결과가 모두 오면 이렇게 안내합니다. "`/ios-plan <작업>`으로 이어가세요."

## 플랫폼 조사 프롬프트

```
기능: <주제>

이 기능을 Apple 플랫폼에서 어떻게 구현하는 게 맞는지 조사하고,
당신의 보고 형식대로 접근법 후보와 트레이드오프를 돌려주세요.

먼저 최소 지원 버전과 기존 의존성을 확인하고 시작합니다. 그게 모든 답의 전제입니다.
API 시그니처와 도입 버전은 반드시 공식 문서에서 확인하고 출처 URL을 답니다.
저장소 내부 구조는 보지 않습니다. 그건 다른 조사가 맡습니다.
```

## 저장소 조사 프롬프트

```
주제: <주제>

이 저장소를 조사하고 당신의 보고 형식대로 결과를 돌려주세요. 범위는 네 가지입니다.

1. **어디를 고치는가** — 관련 타입/뷰/뷰모델/서비스/테스트의 `파일:줄`
2. **이미 어떻게 하는가** — 같은 문제를 푸는 기존 코드. 있으면 그게 기준입니다
3. **제약** — 최소 지원 버전, 액터 격리, 의존성 방향, 기존 테스트가 고정한 동작
4. **깨질 수 있는 곳** — 이 변경이 건드리는 다른 지점

Apple API 가용성이나 프레임워크 선택은 판단하지 않습니다. 그건 다른 조사가 맡습니다.
파일을 수정하지 말고, 계획도 세우지 마세요. 사실만 보고합니다.
판단이 갈리는 지점은 결론 내지 말고 "열린 질문"에 남기세요.
```
